# Reusable UI from Doerr for Ayywi

Source review: 2026-10-24. Recommendations only; no components implemented.

## Scope and recommendation

Compared Ayywi's 74 component-family metadata files and relevant implementations with Doerr's UI components, styles and consumers. Used the current local source, including Ayywi's uncommitted additions. Doerr declares `@danitesler/ayywi` `^0.1.2`; a feature present locally is not evidence that it has been published.

Many candidates already have React components in Doerr. The gap is that they depend on Doerr's store, models, selectors or actions, or remain repeated compositions rather than portable Ayywi contracts.

Start with inline editing, record picking, property rows and tree navigation. Then extract the repeated board and calendar structures. Keep application state, persistence, file formats and scheduling policy with consumers.

Priority reflects likely reuse across projects, observed repetition in Doerr, the gap in Ayywi, and extraction complexity. Cross-project use cases below are recommendations, not verified demand from other repositories. Effort is relative and includes documentation and framework parity, not just copying JSX.

## Existing coverage to reuse

| Apparent gap in Doerr | What Ayywi already provides | Decision |
| --- | --- | --- |
| Sidebar and detail resizing | `AppShellResize`, `AppShellDetail`, width hooks and keyboard resizing in `src/components/app-shell/` | No new splitter needed for these panes. A standalone splitter would require a separate demonstrated use case. |
| Generic drag and reorder | `src/components/drag-drop/` has pointer and keyboard support, sortable areas, acceptance rules, previews and insertion edges. | Reuse it. Tree nesting is an extension, not a reason to transplant `lib/dnd.ts` wholesale. |
| Table column resizing, pinning, reordering, row reordering and basic inline edit | `src/components/table/table.react.tsx`, `table.ts` and metadata | Extend the existing table and editing behavior. Doerr's typed cells do not justify another table family. |
| Date selection | `DatePickerGrid`, date/time/range pickers | Doerr's `DateGrid` already wraps `DatePickerGrid`. Only event-calendar and recurrence composition are new candidates. |
| Filters, active chips and sorting | Filter bar, Chip, Menu, Search bar and Sorting | Add the condition-building interaction, not another bar. |
| Editor toolbars and colour controls | Toolbar, Menu, Swatch and Color picker | `DocTools.Tool`, `ColorTool`, `FontPick` and `SizePick` mostly compose existing controls. Improve examples or add a targeted missing prop before creating new families. |
| Statistics and habit progress | Chart (including heatmaps), Stat, Progress and Progress ring | Extract no generic chart or ring duplicate. An interactive history calendar could be an event-calendar example later. |
| Feedback, shortcuts and blank states | Toast actions, Alert, Shortcut help/recorder, Empty state and Skeleton | Reuse existing contracts; reminder delivery and application-specific illustrations remain in Doerr. |

## Extraction constraints

- Ayywi's product is a token-driven CSS class contract with framework-free behavior, thin React wrappers and light-DOM elements where interaction needs them. Moving a Doerr React file alone does not finish an extraction.
- Remove `useStore`, application actions, `Task`/`Database`/`Folder` assumptions and Tauri imports. Use controlled values, slots, neutral IDs and intent callbacks. Keep persistence, validation of business rules and undo history in consumers.
- Preserve RTL and density behavior. Verify focus, keyboard operation, IME input, long labels, empty/loading/error/disabled states, theme contrast and forced colours before promoting borrowed behavior. Existing Doerr code is source material, not proof of a complete portable accessibility contract.
- Reuse existing internals before creating another family. Especially share `TableEdit` draft/commit behavior, Combobox navigation, floating placement and Drag drop. Let the app decide how dates, records and queries are interpreted.
- Publish metadata, HTML and React examples with the feature so Ayywi's generated docs, manifest and AI tooling can recommend it. Follow the repository's component checklist and required checks during implementation.

## Suggested order of work

1. Inline edit, record picker and property rows: the smallest group that improves detail pages, database cells, rename flows and relations together.
2. Tree: build on those pieces and add hierarchy-specific drag behavior to the shared drag system.
3. Confirm helpers, Board and Event calendar: each has direct reuse evidence inside Doerr. Migrate task and database versions to the same public contracts to prove the board and calendar APIs.
4. Condition builder, Find bar and Emoji picker.
5. Add the lower-priority patterns as examples first, and promote only the interactions that still require repeated application code.

## Review limits

This is a source analysis, not a runtime visual, accessibility or performance audit. No browser or desktop app was launched. Priority is a product/engineering recommendation rather than measured adoption. Full block/rich-text editors, spreadsheet virtualization/formulas, canvas geometry, PDF annotations/signatures, Office codecs, vault sync and notification delivery were deliberately excluded from Ayywi core; they need their own scope and maintenance decision.
